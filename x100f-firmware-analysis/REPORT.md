# FUJIFILM X100F ファームウェア Ver.2.12 静的解析レポート

- 対象: `FPUPDATE.DAT`（公式配布、2024-11-28 公開、53,544,672 バイト）
- SHA-256: `c0d4c31985aaf793e060924fbfdfbd7cf205a27986cda43c1806688e01523f89`
- 方法: 静的解析のみ（実機での実行、書き換え、書き込みはしていない）
- 使ったもの: Python（`tools/` 以下の自作スクリプト）、Capstone、binwalk、radare2
  - Ghidra は GitHub からしか入手できず、解析環境のネットワーク制限で取得できなかった。代わりに、手元の Ghidra でそのまま開けるインポートスクリプトを同梱した（後述）。

## 1. 表層調査

### 1.1 更新ファイルのヘッダ（0x000–0x213）

| オフセット | 値 | 意味 |
|---|---|---|
| 0x000 | `4` | ヘッダ形式（fujihack の分類で 3–8 は 512 バイトの機種コード欄を持つ形式） |
| 0x004–0x203 | ASCII の 16 進 | 機種コード 14 個: `00052271 … 00052300`（仕向け地違い） |
| 0x204 / 0x208 | `2` / `0x12` | バージョン 2.12（16 進で表記） |
| 0x20C | `0x0F6F9B3D` | チェックサム。**計算方法は未解明**（下記参照） |
| 0x210 | `1` | 機器種別（1 = カメラ、2 = レンズ） |

チェックサムは、fujihack の Wiki にある「全バイトの合計」、復号前後の 8/16/32 ビット合計、先頭や末尾の範囲を絞った合計、CRC32、Adler-32 のどれとも一致しなかった。この世代では方式が変わっているとみられる。書き換えをしない限り必要ないので、ここで打ち切った。

### 1.2 難読化

ヘッダより後ろ（ペイロード）は、**全バイトがビット反転（`~b`、つまり XOR 0xFF）**されているだけ。暗号化はされていない。復号すると ARM 命令がそのまま読める。

### 1.3 ペイロードはフラッシュメモリのイメージ

- **ペイロードのオフセット 0x48 = フラッシュのアドレス 0xF0000000**。各領域は 64KB 境界＋0x48 から始まる。
- フラッシュの先頭には `FFFFFFFF 00000000 55555555 AAAAAAAA`、分岐命令、`0xF0000A10` へのポインタが並ぶ。ブートローダーの関数 `0xA0B8` がちょうどこの並びを確認している。
- ペイロードの 0x0–0x47 と、フラッシュ末尾より後ろ（0x3310048–）には、更新処理用とみられるメタデータがある（未解析）。

## 2. 展開（アンパック）

### 2.1 パーティション表（フラッシュ 0x120000 → RAM 0x950000）

ブートローダーは、フラッシュ 0x120000 から 0x400 バイトを RAM 0x950000 に写して使う。1 エントリは 9 ワード（0x24 バイト）で、中身は `id, load, size, end, bss, flash_off, flash_size, hdr, compressed`。

| ID | 配置先（load） | サイズ | BSS | フラッシュ | 圧縮 | 中身 |
|---|---|---|---|---|---|---|
| 0 | 0x00040000 | 0x1BB00 | 0x243C0 | 0x060000 | – | ブート段（ThreadX、syslog） |
| 1 | (0x001E0000) | 0x433C90 | – | 0x1270000 | – | UI グラフィック（RGBA） |
| 2 | (0x006F0000) | 0x90330 | – | 0x1830000 | – | リソース |
| 3 | 0x00950400 | 0x39A80 | 0x57E60 | 0x130000 | – | アップデータ A（FAT、DCIM、SD カード処理） |
| 4 | 0x00A50400 | 0x39A80 | 0x57E60 | 0x1B0000 | – | アップデータ B（A を別アドレス向けにリンクしたもの） |
| 5 | 0x00B51000 | 0x412000 | 0x3F9000 | 0x230000 | **あり** | OS・ライブラリ層（ThreadX、libc など。メインから約 8,200 回呼ばれる） |
| 6 | 0x0135C000 | 0x66F000 | 0x92F000 | 0x420000 | **あり** | コード（メインから約 1,000 回呼ばれる） |
| 7 | 0x022FA000 | 0x7E9000 | – | 0x7D0000 | – | **メインアプリ**（text 0x5B8000 と、データ 0x28B2000 / 0x28B9000） |

- 配置先＋サイズ＋BSS が次の領域の先頭とぴったり一致する（ID5 → 0x135C000、ID6 → 0x22FA000）。表の読み方が正しい裏付けになる。
- 各領域のロードアドレスは、「コード中の絶対アドレスが文字列の先頭を正しく指すか」で検証した。メインは文字列 4,130 個のうち 3,304 個、アップデータは 26 個のうち 24 個、ブート段は 7 個のうち 6 個が参照されている。

### 2.2 圧縮パーティション（ID5 / ID6）— 展開に成功

- ヘッダの並び: `展開後サイズ, 圧縮サイズ, ブロック数, 0x4000, フラグ`（各 4 バイト、計 0x14 バイト）。
- **圧縮形式を解読し、ID5 / ID6 とも完全展開できた。**（詳細と検証は 4 章。ツールは `tools/x100f_lzss.py`）
  - ID5: 0x1EB675 → **0x411D14 バイト**（ぴったり）
  - ID6: 0x3A0FDD → **0x66F000 バイト**（ぴったり）
- 実機のブートでは SoC 内蔵の展開エンジン（レジスタ 0xFFF80020 / 0xFFF80028）が展開するが、**形式自体は 2KB 窓の素直な LZSS で、ソフトで再現できる**。ブートローダーの関数 `0x910` は、`hwdec_init`（0x9E0C）→ フラッシュ読み込みに 16KB ごとのコールバック（0x9E7C）を渡してエンジンへ流し込み → `hwdec_finish`（0x9EA4）で完了待ち、の順で処理する（16KB はエンジンへ送る単位で、展開の窓とは別）。
- 展開後の中身（従来は断片的にしか読めなかったもの）:
  - GPU: **OpenGL ES-CM 1.1**、DMP 社の **EGL ドライバ**（`src/egl/client/dmpdevconf.c`）。拡張に `GL_DMP_*`（DMP の PICA 系 GPU）
  - 画像: JPEG / MPO エンコーダ、RAW 現像（`recbf*` / `reccf*` / `PRAF_*`）
  - ライブラリ: libc 相当（strcmp・memcpy など、メインアプリが呼ぶ関数が正しいアドレスに出現）、内部コマンド名 `uicom_svc_*` 多数
  - Wi-Fi 転送のリサイズ設定 `MSG_ITEM_WLAN_3MRESIZE`、`H21_WRN_CANNOT_RESIZE_RAW_F`（RAW はリサイズ不可の警告）
- **結論: 独自形式で、完全な静的展開はできていない。** ただし「ハードウェア専用の不透明なブロブ」ではなく、リテラルが生で残る LZ であることを突き止め、文字列レベルの中身は取り出せた。完全展開には、実機の RAM 吸い出しか、エンジン仕様の推定が必要。

## 3. 逆アセンブル（メインアプリ 0x022FA000）

- ARM（A32）、フレームポインタあり、アドレスは `movw/movt` の組で作る書き方（GCC）。
- BL 命令は約 108,000 個、`push {…, lr}` で始まる関数は少なくとも約 9,400 個。
- 呼び出し先の内訳: メイン内 96,712、ID5 8,230、ID6 964。OS や libc の多くは圧縮された ID5 側にある。

### 3.3 逆アセンブルの品質を数値で検証

「本物の ARM/Thumb で、capstone できれいに読める」という一般的な言われ方を、実データで裏を取った。capstone がデコードできる割合だけでは弱い（乱数でも ARM として 87% はデコードできてしまう）ので、**BL 命令の飛び先が関数の入口（`push {…, lr}`）に当たる割合**も測った。本物のコードなら高く、乱数なら 0% 近くになる。`tools/codecheck.py` で計測。

| 領域 | ARM デコード成功率 | BL の飛び先が関数入口（ARM） | 同（Thumb） |
|---|---|---|---|
| メインアプリ 0x022FA000 | 99.98% | **87.0%** | 0% |
| アップデータ 0x950400 | 99.55% | **66.2%** | 0% |
| ThreadX ブート段 0x40000 | 99.99% | **26.4%** | 0% |
| ブートローダー 0x0 | 98.59% | **30.3%** | 0% |
| 圧縮 ID5 | 91.60% | 0.0% | 0% |
| 圧縮 ID6 | 90.81% | 0.0% | 0% |
| 乱数（比較用） | 86.99% | 0.0% | 0% |

- **ARM（A32）は本物。** 無圧縮の 4 領域は、関数の入口・呼び出し・定数読み込み（`movw/movt`）が素直に並ぶ。ブート 2 段の割合が低めなのは `push {…, lr}` を使わない小関数が多いためで、乱数の 0% とは明確に違う。
- **Thumb はどこにもない。** 全領域で Thumb の BL は関数入口に一度も当たらない。「ARM/Thumb で読める」という言い方のうち Thumb は当てはまらない。
- **圧縮領域はコードとして読めない。** デコード成功率は乱数と同じ 87% 近辺で、飛び先一致は 0%。見かけ上 capstone が「読める」だけで中身は圧縮データ。デコード成功率だけを根拠にすると圧縮領域まで「読める」と誤認しうる。

### 3.4 ブートの流れ（静的に追えた範囲）

1. ブートローダー段 1（フラッシュ 0x20000、アドレス 0 で実行、ARM の例外ベクタ付き）
2. フラッシュ先頭の署名を確認する（`0xA0B8`）
3. パーティション表を 0x950000 に写し、`ptable_find`（0xA68）で ID から探す
4. RAM 0xE1A4 のフラグが 1 のとき、ID0（0x40000）、ID3 / ID4（アップデータ）、ID5（ハードウェア展開で 0xB51000 へ）を順に読み込む。フラグの意味は未解明
5. ID6 とメインアプリの読み込みは後段で行われる（未追跡）

## 4. 圧縮形式の解読（解決）

圧縮パーティション ID5 / ID6 の形式を段階的に突き止め、完全展開に成功した。

### 4.1 解読の手順

1. **リテラルが verbatim（生のまま）である証拠。** 圧縮ストリームの中に、`push` → `mov r0,sp` → `bl` → `pop` → `bx lr` といった連続した本物の ARM 命令が制御バイトを挟まずに並ぶ箇所があり、まず「リテラルはそのままコピーされる形式」と分かった。
2. **枠組みの確定（入力をぴったり消費するか）。** 「制御バイト c<0x80 は長さ c のリテラル・ラン、c≥0x80 は一致（制御＋1 バイト）」という枠組みで解析すると、ストリームを**入力の末尾 0x1EB675 にちょうど到達**して消費し、必要な平均一致長がちょうど 7.00 になった。
3. **長さ符号化の逆算。** 一致値の下位ビットの合計が、必要な一致出力バイト数（0x363581）と**加算定数ちょうど 0 で一致**したのは「長さ = 値 & 0xF」だけだった。残りビットが距離。
4. **答え合わせ。** メインアプリが ID5 内を呼ぶ 574 個のアドレスのうち **292 個（51%）が展開後に `push` 関数入口**に命中。出力長も 0x411D14 にぴったり一致。さらに `strcmp`・`memcpy`・printf 系ログ関数が、メインアプリの呼ぶアドレスちょうどに、教科書どおりの ARM コードとして現れることを確認した。

### 4.2 形式（Milbeaut 系 LZSS）

- ヘッダ 0x14 バイト: `uncompressed_size, compressed_size, num_blocks, block_size(0x4000), flags`（各 LE u32）。
- 本体（0x14 以降）は 2KB 窓の連続トークン列:
  - 制御バイト `c < 0x80` … 続く `c` バイトをそのままコピー（リテラル・ラン）
  - 制御バイト `c ≥ 0x80` … もう 1 バイト `b` を読み、`val = ((c & 0x7F) << 8) | b`（15 ビット）。**長さ = `val & 0x0F`、距離 = `val >> 4`**（1〜2047 バイト前）。距離分だけ前から長さバイトをコピー。
- 実装は `tools/x100f_lzss.py`（標準ライブラリのみ）。ID5 → 0x411D14、ID6 → 0x66F000 を出力（いずれもぴったり）。

### 4.3 展開で新たに読めるようになったもの

- **libc 相当**（strcmp, memcpy, printf 系ログ `dbg_log`=0xC1D860 ほか）
- **RAW 現像パイプライン**（`recbfResize*`, `reccfSetDevelopParaFilmSimulation`, `PRAF_*`）
- **Wi-Fi 転送**の内部（`MSG_ITEM_WLAN_3MRESIZE` = 3M リサイズ設定、`H21_WRN_CANNOT_RESIZE_RAW_F` = RAW はリサイズ不可）
- 内部サービスコマンド `uicom_svc_*` 多数、DMP GPU ドライバ（`GL_DMP_*`）
- これで ID5/ID6 も逆アセンブル対象にでき、従来「圧縮領域にあって追えない」としていた処理（デバッグ画面の呼び出し元、RAF 転送の判定など）を追う土台ができた。

## 5. 本体のチップ（SoC）

- **X-Processor Pro の正体は Socionext（旧富士通セミコン）の Milbeaut 系 SoC** とみられる。今回の解析所見と整合する。
  - RTOS が **ThreadX SMP / Cortex-A7**（マルチコアの ARM。1.4 節）
  - GPU が **DMP 社（Digital Media Professional）の EGL/OpenGL ES ドライバ**（`src/egl/client/dmpdevconf.c`、`OpenGL ES-CM 1.1`）。DMP の PICA 系 GPU は Milbeaut や任天堂 3DS に採用例がある
  - **展開エンジンが 0xFFF80000 台のレジスタを持つ**（Milbeaut のメディア処理 IP に相当）
- **FCC ID は W2Z-02000003**（W2Z = 富士フイルムの grantee コード）。fccid.io に届出書類と内部写真がある。**圧縮形式を解くうえでは、内部写真から SoC の型番を確定し、その TRM（技術リファレンス）や Milbeaut の展開 IP 仕様を当たるのが本筋**。ただし Milbeaut の圧縮 IP の仕様は一般公開されていない。
- **センサー**は X-Trans CMOS III（APS-C、2432 万画素）。センサー自体はファーム内の圧縮形式とは無関係。

## 6. スマホ転送と RAF、ファームの改善点

### 6.1 Wi-Fi 転送の「縛り」— 半分は設定で外せる

ファーム内の根拠と、実際にできること。

- 拡張子を分類する関数（0x28B4EE4）が `.JPG` `.MPO` `.RAF` `.RAW` `.WAV` を区別している。
- RAF を選ぶと `RAWファイルです`（警告アイコン付き）を出して弾く文字列がある（UI 文字列 0x18D2B10 付近）。

**(a) 3M 縮小はロックではなく設定項目**

- ID5 に `MSG_ITEM_WLAN_3MRESIZE` と `MSG_VALM_3MRESIZE_ON/OFF`・`MSG_VALS_3MRESIZE_ON/OFF` がある。`VALM`/`VALS` はメニューの値表示なので、**ユーザーが ON/OFF できる設定**。
- **OFF にすればフル解像度の JPEG がそのままスマホへ送られる。** 「必ず縮小される」わけではない（転送は遅くなる）。
- 関連: `H21_WRN_CANNOT_RESIZE_RAW_F`（RAW はリサイズ不可の警告）。

**(b) RAF をスマホへ送るのは実質不可**

- カメラ側の判定に加え、受け側のスマホアプリが RAF を扱えないため、仮にパッチしても意味が薄い。パッチ自体もチェックサム未解明・文鎮化リスクで非現実的。

**(c) RAW を無線で送るなら PC 保存（PC AutoSave）**

- ファームに独立した PC 保存機能がある: `SERVICE:PCAUTOSAVE/1.0`、`MSG_ITEM_PCSAVE`、`MSG_ITEM_WLAN_PCSAVES`、状態遷移 `PCSAVESEARCH → PCSAVECONNECT → PCSAVESAVING → PCSAVEEND`、画面 `UILIB_SUB_SCR_PC_SAVE_*`。
- スマホ送信（JPEG 専用・縮小あり）とは**別系統で、PC へのバックアップ経路**。RAW を無線で抜く純正ルートはこちら。

### 6.2 ファームの古さ（参考・セキュリティ寄りの改善余地）

いずれも動作に致命的ではないが、古い部品が入っている。

| 部品 | バージョン | 備考 |
|---|---|---|
| SQLite | 3.6.22（2010-01-05） | 画像 DB 用。以降 10 年以上分の修正が未反映だが、外部入力に直接さらされる面は小さい |
| wpa_supplicant | 2003–2011 系、WPS 対応 | WPS（PBC/PIN）は既知の弱点あり。カメラは主に自身が AP になる運用で露出は限定的 |
| 独自 RTOS 層 | VxWorks→NORTi→ThreadX の互換層 | ThreadX 世代。仕組み上、動的メモリ確保をあまり使わない |

- **X100F の最終ファームは 2.12（2024-11-28）** で、富士は既に最後のバグ修正を出している。公式の機能追加は今後見込めない。上記は「古い設計が残っている」という観察であって、実害のある脆弱性を確認したものではない。

## 7. 欠陥の体系的な探索（結果は陰性）

「直っていない計算間違いがないか」を、憶測ではなく機械的な検査で調べた。**結論として、欠陥と断定できる箇所は見つからなかった。** 陰性の結果もファームの品質評価として意味があるので残す。

### 7.1 ジャンプテーブルの境界チェック（`tools/jumptable_check.py`）

`cmp rX, #N` → `ldrls pc, [pc, rX, lsl #2]` という分岐表を全領域から抽出し、「N 以下を許すなら表に N+1 個の妥当な飛び先があるか」を検証した。境界が 1 つずれていれば表の外（データ）へ飛ぶ実害のある不具合になる。

| 領域 | 検査したジャンプテーブル | 境界の誤り |
|---|---|---|
| メインアプリ | 499 | 0 |
| ID5 os/lib | 523 | 0 |
| ID6 code | 1059 | 0 |
| 合計 | **2081** | **0** |

（1 件の警告は、飛び先の先頭ワードが条件フィールド 0xF を持つ命令だったための判定側の誤検出。）

### 7.2 ゼロ除算・桁あふれの走査（`tools/calcbug_scan.py`）

約 480 万命令を走査し、(1) 除数がゼロ検査されていない除算、(2) 掛け算の結果を 16 ビットへ切り詰めている箇所、を抽出した。生の件数は除算 約 1960 件・切り詰め 約 120 件だが、**大半は文脈を見れば誤検出**。

### 7.3 最有力候補の追跡（結果: 正しく守られていた）

最も疑わしい経路を最後まで追った。

1. 除数を返すアクセサ（0x25DAC88 / 0x25DACE4）が、**範囲外の ID に対して 0 を返す**（`movhi r0, #0` で即リターン）。
2. 呼び出し元 0x22FC60C はその戻り値で `sdiv` している（ゼロ検査なし）。
3. → ゼロ除算の疑い。

しかし検証の結果:

- **呼び出し元 0x22FC60C も同じ範囲チェックを自前で行っていた**（0x22FC698: `add r2, r4, #0x1000000` / `cmp r2, #0xABD` / `bhi` で割り算ごと飛ばす）。二重に守られている。
- 「範囲内でも表の値が 0 なら危険」という残る懸念も、参照先の表（ID1 内 0x341648、12 バイト × 2750 項目）を実際に読み出して確認し、**幅・高さともに 0 の項目は 0 件**だった。
- アクセサの呼び出し 59 箇所のうち、戻り値で除算しているのはこの 1 関数だけ。

### 7.4 静的解析の限界

断定できない理由は構造的なもの。変数の**正しい値の範囲**が不明（仕様書がない）、**実行して確かめられない**（実機がない）、ソースもシンボルもないため意図が読めない。残る候補を 1 件ずつ潰すことは可能だが、当たりかどうかは最終的に実機での再現が要る。

## 8. 設定・機能の棚卸し（実用編）

ファームを書き換えなくても使える情報として、内部の設定項目を抽出した。メニュー項目は全体で **372 個**（`MSG_ITEM_*`）。

### 8.1 フィルムシミュレーションブラケットの 3 枠は指定できる

`MSG_ITEM_FILMBKTSET_FILM1 / FILM2 / FILM3` があり、選択肢として次が並ぶ。

```
STD(PROVIA) / VELV(Velvia) / SOFT(ASTIA) / CCROME(クラシッククローム)
NEGAH(PRO Neg.Hi) / NEGAS(PRO Neg.Std) / SEP(セピア)
MONO + MONOY/MONOR/MONOG(モノクロ＋各フィルター)
ACROS + ACROSY/ACROSR/ACROSG(ACROS＋各フィルター)
```

**フィルムシミュレーション BKT で撮る 3 種類を自分で選べる。** 1 回のレリーズで 3 つの味を同時に書き出せるので、レシピ作りの比較に向く。

### 8.2 Fn ボタンに割り当てられる機能（36 種類）

```
AE / AELOCK / AFAELOCK / AFLOCK / AFON / AFAREA / AFMODE
FILMSIM / GRAIN / DRNG / WB / ISOAUTO / QUAL / RAW / PIXEL
NDFILTER / CONVLENS / CONTRING / FNUMCONTROL / SHUTTERTYPE
FACE_EYE / PINTCHK / FCHECK / EVPREVIEW / EXPPREVIEW / EVFFILM
TTLLOCK / MODELINGFLASH / STROBE / MICLV / MANNER / TIMER
OSDLARGE / PLAYMODE / CSET / WLAN / NONE
```

見落とされがちなもの: **GRAIN**（粒状感の切替）、**CONTRING**（コントロールリングの機能切替）、**TTLLOCK**（調光量ロック）、**EVFFILM**（ファインダーへのフィルムシミュレーション反映）、**OSDLARGE**（Ver.2.10 で追加された大きい表示）。

### 8.3 画面に表示する項目（27 種類、`MSG_ITEM_DSPCUS_*`）

```
FOCUS / DISTG / DISTGMF(距離指標・MF時距離指標) / HISTGR(ヒストグラム)
LEVEL(電子水準器) / FRAME / DISPLAYFRAME / TARGETMARK
DR / EC / EV / AE / WB / FILMSIM / SFISO / DRIVE / RECMODE
PIXQLTY / TAKENUM(残り枚数) / BTTRY / FLSH / MICLV / MOVIE
BACKGROUND BLURRING(背景ぼけの目安) / DIGITELECON / CONVLENS
ELECTRONICSHUTTER
```

### 8.4 内部の現像パラメータ構造

デバッグ用の状態ダンプ関数（ID6 の 0x14D62D8）が、設定構造体から連続するバイト列を読んで出力している。

```
ISO      [idx] : 11 個の値
RAW      [idx] : 11 個の値
FSIM     [idx] : 11 個の値   ← 構造体オフセット 0xBC06〜0xBC11
CONTRAST [idx] : 11 個の値   ← 0xBC14〜
SHARP    [idx] : 11 個の値
SDW-TONE [idx] : 11 個の値
```

いずれも**実行時の RAM 上の状態**であり、静的なファームからは既定値表を直接は取り出せなかった。実機のデバッグシリアルが使えれば、この形式で現在値を読み出せる。

## 9. やっていないこと・注意

- ファームウェアの改変、再パック、書き込みはしていない。再パック用のツールも用意していない。チェックサムが未解明なので、改変したファイルはおそらく受け付けられない。無理に書き込めば起動不能になるおそれが高い。
- ファームウェア本体と、そこから切り出したバイナリはリポジトリに含めていない（公式サイトから各自ダウンロードする前提）。
- ダウンロード時に同意する富士フイルムの使用許諾の条件は、各自で確認すること。
